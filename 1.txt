下面把 **13 个 Grill Session 问题对应的回答**分别总结成一段，方便你整理设计文档。

---

## 1. DB Package 如何被 Nuxt Nitro 消费？

`packages/db` 应作为独立 workspace package，通过 pnpm workspace 方式被 `apps/web` 引入，而不是额外 build。`apps/web/server` 中直接通过 `@vibe/db` 使用 Drizzle 的 schema 和数据库实例。数据库 migration 应归属于 `packages/db` 管理，由 db package 提供独立命令执行，例如 `pnpm db:migrate`，避免让 Web 应用承担数据库结构管理职责。

---

## 2. Devlog 双数据源如何解决？

取消 Devlog 的数据库存储，避免 SQLite 和 Markdown 两套数据源产生同步问题。博客文章属于动态内容，继续使用数据库 `posts` 表管理；开发日志属于项目过程记录，使用 `docs/devlog/*.md` 配合 Nuxt Content 管理。这样 Blog 和 Devlog 职责分离，数据库负责业务数据，Markdown 负责版本化文档。

---

## 3. 浏览器端模型首次下载体验如何优化？

WebLLM/Transformers.js 本地模型需要增加模型生命周期管理机制，包括未下载、下载中、已完成、失败等状态。首次进入 Local AI 模式时，不自动下载，而是向用户展示模型大小、下载进度和确认按钮；模型使用浏览器缓存或 IndexedDB 保存，并支持失败重试和断点恢复，提高本地 AI 的使用体验。

---

## 4. Prompt Playground 草稿丢失问题如何解决？

Playground 需要增加草稿状态管理机制。用户修改 Prompt 或填写变量后，前端保存当前编辑状态，并在切换模板或离开页面时检测未保存内容，提示用户确认。同时可以结合 localStorage 实现自动保存，避免用户因为误操作导致测试内容丢失。

---

## 5. promptRuns.output 无限增长如何处理？

Prompt 运行记录需要控制数据规模。`promptRuns` 可以保留输出结果，但增加 token 数量、创建时间等字段，并限制单次输出大小，例如超过一定长度进行截断。未来如果支持图片、文件等大资源，可以将结果迁移到独立的 artifact 存储，而不是全部保存在 SQLite 中。

---

## 6. Prompt 变量缺失如何处理？

变量系统采用严格校验策略。在执行 Prompt 前，先解析模板中的变量，例如 `{{name}}`，生成必填变量列表。如果用户没有填写完整变量，则阻止运行并提示缺失字段，而不是将空值或原始占位符发送给模型，保证 Prompt 执行结果可控。

---

## 7. Chat 会话中途切换模型怎么办？

模型选择粒度应该从 Session 级调整到 Message 级。`chat_sessions` 只保存会话信息，具体每条消息记录使用的模型、provider、响应时间等信息放入 `chat_messages`。这样用户可以在同一个会话中自由切换 Local AI 和 Cloud AI，同时保留完整推理历史。

---

## 8. 浏览器内存检测兼容性如何解决？

不能完全依赖 `navigator.deviceMemory`，因为 Safari 和 Firefox 可能不支持。Local AI 是否可用应该综合判断 WebGPU 支持情况、浏览器能力和用户主动选择。默认可以使用 Cloud 模式，当检测到支持本地推理环境时，再向用户提供开启 Local AI 的选项，而不是直接禁用。

---

## 9. PM2 多实例和 SQLite 写锁冲突如何解决？

由于项目定位是个人工具站，不需要 PM2 cluster 多实例部署。采用单实例运行即可，同时开启 SQLite WAL 模式提升并发能力，并增加简单的错误重试机制。部署方式更推荐 Docker 单容器运行，保持架构简单稳定。

---

## 10. 域名和服务器如何处理？

不要把线上访问作为前期开发硬依赖。开发阶段先保证 Docker 部署可运行，公网部署作为后续阶段。如果部署，需要提前准备服务器和域名；国内服务器需要备案，想快速展示可以选择香港或海外节点。使用 Caddy 自动配置 HTTPS，完成从代码到线上访问的完整流程。

---

## 11. Week2 AI 开发计划是否过紧？

原计划低估了 WebLLM 的实现复杂度。应该调整开发顺序：先完成 Cloud AI Chat，跑通 SSE、历史记录和基础交互；之后开发 Prompt Studio；最后再加入 WebLLM 本地推理。这样可以保证核心产品先上线，再逐步增加端侧 AI 亮点。

---

## 12. 测试策略如何加强？

测试重点应该围绕核心业务流程，而不是简单覆盖页面。需要增加 Prompt 变量解析、模板渲染、模型调用失败、SSE 中断、模型切换、草稿保存等测试场景。Prompt Studio 作为项目核心能力，需要保证关键链路稳定，而不是只验证一次成功调用。

---

## 13. 公开部署没有认证是否安全？

公开部署的 AI 接口不能完全裸露，否则可能导致 API 滥用和费用风险。对于个人工具站，不需要复杂 OAuth，可以增加简单 Access Token 认证，同时结合 IP 限流控制请求频率。这样既保证安全性，也不会引入过多开发成本。

---

# 最终修改方向总结

把原设计调整为：

```text
Vibe Station

Nuxt3 Monorepo

├── apps/web
│   ├── 前端
│   └── Nitro API
│
├── packages
│   ├── db
│   ├── shared
│   └── ai-core
│
└── docs/devlog
```

核心原则：

1. **单一数据源**
2. **Cloud AI 先行，Local AI 后置**
3. **模型能力模块化**
4. **数据库、部署、测试按照生产思路设计**
5. **控制复杂度，不为了展示功能牺牲稳定性**

这样修改后，Vibe Station 会更像一个真实 AI 工程项目，而不是一个 AI 功能集合 Demo。
